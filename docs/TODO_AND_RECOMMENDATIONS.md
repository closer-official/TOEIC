## 5. 実装すべき・強化すべきと考える箇所

### 5.1 取引

- **exchange_daily_snapshots の投入**  
  日次で `profiles` から `gems` と `evolution_points` を集計し、前日分を `exchange_daily_snapshots` に INSERTする処理（cron / Supabase Edge Function / 外部スクリプトのいずれか）を実装する。

### 5.2 進化

- **合成機能**  
  「合成する」の仕様（何と何を合成して何になるか）を決め、API・DB・UI を実装する。未実装のままならボタンや説明を「準備中」に合わせて整理する。

### 5.3 設定

- **通知ON/OFF**  
  ブラウザ通知やアプリ内通知の許可・OFF 設定があるとよい。
- **テーマ**  
  ダーク/ライト切り替え（既にダーク前提なら不要の可能性あり）。
- **アカウント連携**  
  連携解除・連携先の表示など、必要に応じて実装。
- **アカウント削除**  
  ストア審査や GDPR 対応のため、削除フローとデータ消去の実装を検討。

### 5.4 コンテンツ・サポート

- **FAQ**  
  課金・解約・不具合・問い合わせ先などをまとめた本文を用意する。
- **会社概要・運営者情報**  
  運営者名・連絡先・住所を `/about` に記載する。
- **問い合わせ**  
  サポート用メールアドレスまたはフォームを、設定・FAQ・フッターなどに明示する。

### 5.5 課金（有料化する場合）

- 決済リンク（Stripe 等）の実URL・商品IDの設定。
- 購入状態を保存するテーブル（例: `subscriptions`, `purchases`）と API。
- プレイ可能回数を「課金状態」に応じて返す API、またはゲーム開始時の課金チェック。
- 特定商取引法に基づく表記ページ。
- 返金・解約の記載と、必要なら復元（リストア）の実装。

### 5.6 セキュリティ・運用

- **利用規約・プライバシーへの同意**  
  初回利用時や会員登録時に「同意する」チェックとその記録があるとよい。
- **環境変数・シークレット**  
  本番では Vercel 等の環境変数で管理し、リポジトリにコミットしないことを確認。

### 5.7 ゲーム・仕様

- **SPEC-SURVIVAL-CLOCK.md**  
  サバイバル・クロックの「仕様書」はあるが、**現状のゲームには未実装**と明記されている。実装する場合はこの仕様を参照する想定。
- **単語 For You のカウントダウン**  
  ゲーム画面で「準備中...」が出るパターンがあるため、表示条件や文言の整理を検討する。

### 5.8 マーケットプレイス（取引）

- **出品の DELETE ポリシー**  
  出品取り消しは `status = 'cancelled'` の UPDATE で実装されているため、現状の RLS（SELECT/INSERT/UPDATE）で足りる。DELETE は使っていない。
- **購入者への通知**  
  購入成立時に販売者へ「売れました」などの通知があるとよい（任意）。
