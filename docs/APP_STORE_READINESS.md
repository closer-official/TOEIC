# App Store（ストア公開）に向けた不足箇所一覧

現状のコードベースを調査した結果です。**支払いまわりの把握範囲**と**不足している項目**をまとめています。

---

## 支払い・課金について（把握している範囲）

### 実装されていること

| 項目 | 場所 | 内容 |
|------|------|------|
| ペイウォールUI | `src/components/PaywallModal.tsx` | 「本日1回の無料プレイが終了しました」モーダル。「100円パス」「サブスクを確認」ボタンあり。 |
| 購入リンク | 同上 | `https://billing.stripe.com/pay/placeholder` の**プレースホルダー**（実リンク未設定）。 |
| 無料プレイ制限 | `src/lib/dailyLimit.ts` | 初回7日間は無制限、以降は**1日1回まで無料**。`localStorage` で日付・回数を管理。 |
| 制限判定 | `src/app/game/page.tsx` | ゲーム開始前に `canPlayFreeToday()` で判定。`false` なら `PaywallModal` を表示。 |

### 実装されていない・不明なこと

- **決済の実処理**  
  Stripe（または他プロバイダ）の Checkout / Payment Links / サブスクの**実URL・商品ID・価格**は未設定。プレースホルダーのまま。
- **購入状態の永続化**  
  「100円パス購入済み」「サブスク有効」などを保存するテーブル・API・フロント連携は**なし**。`dailyLimit` はローカルのみで、課金状態を見ていない。
- **サーバー側の制限**  
  プレイ可能回数は**クライアントの `canPlayFreeToday()` のみ**。localStorage の改ざんや無効化で制限を回避できる状態。
- **領収書・返金・解約**  
  IAP（Apple/Google）や Stripe の領収書・返金・解約フローの実装は**なし**。
- **税・表示**  
  価格の税込/税抜、ストア用の価格表示（例: ¥100）の定義や表示ロジックは**なし**。

**まとめ**: 支払いについては「課金が必要であることの案内UI」と「ローカルだけの無料回数制限」まで。**実際の課金・購入状態の管理・サーバー側の制限は未実装**です。

## 不足している箇所（ストア公開を想定）

### 1. 法的・ランディング

| 項目 | 現状 | 必要な対応 |
|------|------|------------|
| **利用規約** | `/terms` が「準備中です。」のみ | 本文の作成・掲載。有料提供する場合は料金・解約・禁止事項を明記。 |
| **プライバシーポリシー** | ページ自体がない（`/privacy` 等も未実装） | 作成・掲載。収集するデータ（Supabase の auth/profiles/runs 等）、Cookie、第三者（Supabase/Stripe 等）への提供を記載。App Store 審査では必須。 |
| **特定商取引法に基づく表記** | 未実装 | 有料販売する場合、事業者名・連絡先・返金等の表記が必要。 |
| **会社概要 / 運営者情報** | `/about` は「準備中」 | 運営者名・連絡先・住所等の記載。 |

### 2. 課金・購入

| 項目 | 現状 | 必要な対応 |
|------|------|------------|
| **決済リンク** | プレースホルダーURL | Stripe（または他）の実際の Payment Link / Checkout / サブスクURL に差し替え。 |
| **購入状態の管理** | なし | DB（例: `subscriptions` や `purchases`）と API で「パス購入済み」「サブスク有効」を管理し、サーバーでプレイ可否を判定。 |
| **サーバー側のプレイ制限** | なし | 課金状態に応じてプレイ可能回数を API で返すか、ゲーム開始 API で課金チェックを行う。 |
| **復元（リストア）** | なし | サブスク／アプリ内課金の場合は、同一アカウントでの「購入の復元」対応が審査で求められることがある。 |

### 3. アプリの種類（Web vs ネイティブ）

- 現在は **Next.js の Web アプリ**（Vercel デプロイ）であり、**iOS/Android ネイティブアプリのビルドはありません**。
- **Apple App Store / Google Play に出す**場合は、次のいずれかが必要です：
  - **PWA** として「ホームに追加」で使ってもらう（ストアには出さない）
  - **Capacitor / Expo** 等でラップしてネイティブビルドし、ストアに提出
- ネイティブ化する場合の追加不足例：
  - アプリアイコン（各種解像度）
  - スプラッシュ画面
  - App Store / Play 用の説明文・スクリーンショット・キーワード
  - Apple の App Store Connect ・ Google Play Console の設定
  - （課金する場合）Apple IAP / Google Play Billing の組み込み

### 4. セキュリティ・運用

| 項目 | 現状 | 必要な対応 |
|------|------|------------|
| **環境変数・シークレット** | `.env.local` 等で Supabase キーを参照 | 本番では Vercel の環境変数などに設定し、リポジトリにコミットしないことを確認。 |
| **認証** | Supabase Auth 使用 | メール/マジックリンク等の導線はある。必要に応じてパスワードポリシー・二要素の検討。 |
| **利用規約・プライバシーへの同意** | 明示的な同意フローなし | 初回利用時や会員登録時に「利用規約・プライバシーに同意する」チェックと記録があるとよい。 |

### 5. コンテンツ・UX

| 項目 | 現状 | 備考 |
|------|------|------|

## 優先度の目安（ストア公開する場合）

1. **必須に近い**: プライバシーポリシー、利用規約の本文、決済リンクの実装または課金状態の管理。
2. **有料化するなら**: 購入状態のDB・API、サーバー側のプレイ制限、特定商取引法表記、返金・解約の記載。
3. **ネイティブアプリで出すなら**: アイコン・スプラッシュ、ストア用説明・スクショ、IAP/Play Billing の検討。
4. **あるとよい**: FAQ、設定、問い合わせ先、エラー案内の統一。

## 支払いについて「コード上で分かること」の要約

- **課金の「入口」**: PaywallModal の「100円パス」「サブスク」ボタン → 現状は **Stripe のプレースホルダーURL** のみ。
- **課金の「結果」**: 購入済みかどうかを保存・参照する**テーブル・API・フロントの状態**は**一切なし**。
- **プレイ制限**: 「1日1回無料」は **localStorage のみ**で判定しているため、**サーバーは課金状態を見ていない**。

そのため、**「支払いをどこまで把握しているか」の答え**は次のとおりです。

- **UI と制限の仕様（無料1回/日、7日間無料）** → コードから把握可能。
- **実際の決済処理・価格・商品ID・サブスクプラン** → コード上には**存在しない**（プレースホルダーのみ）。
- **購入後の「プレイし放題」などの付与** → **未実装**。

以上を踏まえ、ストア公開や有料化のスケジュールに合わせて、利用規約・プライバシーポリシー・決済まわり・購入状態管理から順に対応するのがおすすめです。
