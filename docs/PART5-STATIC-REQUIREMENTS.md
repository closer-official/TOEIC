# Part 5 静的問題 要件・設計（Phase 3）

以前の議論とコードベースから整理した、**リポジトリに追加する Part 5 静的問題 100〜200 問**の要件と設計です。

---

## 1. 目的

- **Supabase が空**でも、または **API キー未設定**でも、Part 5 モードで問題を解けるようにする。
- 品詞・語彙・文法の**バランスの取れた**問題セットをリポジトリに持つ。
- 既存の **Supabase / pipeline 形式** と互換にし、ゲーム画面がそのまま使えるようにする。

---

## 2. 問題形式（アプリが期待する形）

ゲーム側は `supabaseToGameQuestion` で次の形に正規化しています。

| 項目 | 型 | 必須 | 備考 |
|------|-----|------|------|
| **id** | string | ○ | 一意（静的では UUID や `static-1` など） |
| **question** | string | ○ | 空欄は `____`（アンダースコア4つ） |
| **options** | [string, string, string, string] | ○ | 4択（A,B,C,D の順） |
| **correct_index** | number | ○ | 0〜3（0=A, 1=B, 2=C, 3=D） |
| **explanation** | string \| null | △ | 日本語の瞬時解説（20字目安） |
| **category** | string | ○ | 下記カテゴリのいずれか |
| **difficulty** | "500" \| "700" \| "900" | ○ | スコア帯想定 |
| **vocab_map** | Record<string, string[]> | × | 問題文・選択肢の重要語→意味（任意） |
| **created_at** | string | × | 静的では省略可。API で付与するなら ISO 日付 |

### カテゴリ（prompts.ts と統一）

- `品詞` / `時制` / `前置詞` / `語彙` / `接続詞` / `代名詞` / `その他`

### 難易度

- **500**: 短い文・基本語彙・選択肢の違いが明確
- **700**: 中程度の文・ビジネス語彙・やや紛らわしい選択肢
- **900**: 長め or 複雑・難語・日本人がよく間違える引っかけ

---

## 3. 既存の静的文件との違い

| 項目 | 既存 `data/toeic-part5-50.json` | 今回の静的問題（推奨） |
|------|----------------------------------|-------------------------|
| 正解の指定 | **answer**: "A"\|"B"\|"C"\|"D" | **correct_index**: 0〜3 |
| id | なし | あり（API で一意 id を付与するため） |
| difficulty | なし | あり（500/700/900） |
| vocab_map | なし | 任意（あれば語彙連携に使える） |

既存 50 問は「品詞」中心で、**answer が文字**のため、API で読み込む際に **correct_index へ変換**する必要があります。

---

## 4. 追加時の品質チェック（本質的に TOEIC の点数が上がるか）

**問題を追加するたびに、以下を満たしているか確認する。**

| チェック項目 | 内容 |
|--------------|------|
| **本番パターン** | 本番の Part 5 で実際に出るパターンか（品詞・時制・前置詞・語彙・接続詞・代名詞のいずれかで、公式・対策本で扱われるタイプか）。 |
| **正解の一意性** | 文脈上、正解が**1つだけ**に決まるか。他3つは文法的・意味的に明らかに誤りか。 |
| **トピック** | ビジネス・オフィス・契約・メール・会議・人事・物流・財務など、TOEIC で頻出のトピックか。 |
| **選択肢の質** | 選択肢が「形が似た品詞違い」「よくある学習者誤答」を反映しているか（本番の引っかけに近いか）。 |
| **難易度の妥当性** | 500＝基礎・700＝実務・900＝上級の目安に合っているか。 |
| **解説の有用性** | explanation が「なぜその選択肢が正解か」を短く示しており、本番で同じパターンに気づける内容か。 |

**除外するもの**: 本番ではほぼ出ないマニアックな文法・学術トピック・冗長な文。  
**追加後**: 既存問題と重複パターンになりすぎていないか、カテゴリ・難易度の偏りがないかを確認する。

---

## 5. バランス（TOEIC 出題傾向に合わせる）

公式・対策本の目安に合わせて、**品詞 40%・語彙 30%・文法 30%** 程度にする。

| カテゴリ | 目安割合 | 100 問の場合 | 200 問の場合 |
|----------|----------|--------------|--------------|
| 品詞 | 40% | 40 問 | 80 問 |
| 語彙 | 30% | 30 問 | 60 問 |
| 時制 | 約 10% | 10 問 | 20 問 |
| 前置詞 | 約 10% | 10 問 | 20 問 |
| 接続詞 | 約 5% | 5 問 | 10 問 |
| 代名詞 | 約 5% | 5 問 | 10 問 |
| その他 | 残り | 適宜 | 適宜 |

難易度は **500 / 700 / 900 を均等**、または 700 を多めにしてもよい。

---

## 6. 実装方針（API のフォールバック）

1. **静的データ**  
   - 新規: `data/part5-static.json`（または既存 `toeic-part5-50.json` を拡張）  
   - 形式: 上記「問題形式」に合わせた JSON 配列。`answer` のみの既存形式の場合は、API 側で `correct_index` に変換する。

2. **API**（`src/app/api/questions/route.ts`）  
   - まず Supabase から取得を試みる。  
   - **データが 0 件**（またはエラー）の場合、静的 JSON を読み、`id` を `static-${index}` などで付与して返す。  
   - 静的の問題には `created_at` がなくてもよい（返却時に `new Date().toISOString()` を付けるか、省略可）。

3. **ゲーム画面**  
   - 変更不要。`supabaseToGameQuestion` に `correct_index` が渡ればそのまま動作する。  
   - 静的問題では `question_id` が `static-1` などのため、ログ送信時もその id でよい（Supabase の `user_logs` に保存する場合は、静的問題用であることが分かれば十分）。

---

## 7. 作業の進め方

1. **形式の確定**  
   - 新規ファイルは `correct_index` + `difficulty` + `category` を持つ形で統一。  
   - 既存 50 問を使う場合は、API で `answer` → `correct_index` 変換を実装。

2. **問題の追加**  
   - まず 50→100 問に増やし（品詞・語彙・時制・前置詞などを追加）、動作確認。  
   - その後 100→150→200 と増やしてもよい。

3. **API のフォールバック実装**  
   - Supabase が空 or エラー時に静的 JSON を返すように `route.ts` を修正。

4. **README**  
   - 「Part 5 は Supabase に問題がない場合は組み込みの静的問題でプレイできます」と記載。
